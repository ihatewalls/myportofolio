1. Debouncing is a technique where we keep cancelling a function until there is no more user input. We need this because we want to implement searching as the user types. If we were to not debounce it, the function would be sent for every single character the user types which causes a lot of requests. To prevent this, we use debouncing to wait for the user to finish what they're typing first.
2. await is used to wait for a fetch() to finish first before using it's response. If we don't use await well we're obviously not going to get the result we wanted because we don't know if the fetch has finished running or not.
3. An XSS attack is when an attack can submit a malicious input to a website that is then displayed to other website viewers. This is usually done through html script tags that causes code to run instantly when a victim loads the page. The reason AJAX is vulnerable is because it doesn't come with a builtin filter that protects agaisnt XSS. Django, on the other hand, has a builtin feature to sanitize inputs within its template engine.

Setup remains the same. This week consists of transitioning from our previous JSON powered system into a system that uses a RESTful API. To start off, the creation of serializers is necessary for the transmission of data between the server and the API. These serializers cover the fields of the existing models and also adds validation checks to ensure data sent through them is valid and safe. Aside from that, we added new api endpoints. In the usage of a RESTful API we can't have multiple endpoints that refer to the same thing when we could just have one that differs based on the type of request. Now to make sure a user is restricted on which requests they can access, we have to set up a permission class. The created permission class filters whether the user is unauthenticated, regular person, editor, or owner, each having their own permissions. These permission classes are then assigned to our functions to apply the restrictions. Aside from that, we also use an authentication class to ensure that the user that is accessing a certain part of the website is logged in. To make sure it all works, we created a new test file that specifically tests apis. The existing test file has been long outdated, being unable to process AJAX and therefore is considered obsolete and irrelevant considering the constant overhauls.

1. REST is short for Representational State Transfer. A RESTful API is an API that follows all of the constraints set by the REST framework. Those being: Client-Server Separation: UI not related to data storage, Stateless: each request provides all of its own context, Cacheable: Declares whether data is cacheable, Uniform Interface: unique identifiers for each resource (uniform for any action), manipulation of data through representation of the resource (json), self-descriptive messages, HATEOAS (hyperlinks), Layered System & Code on Demand: Hidden proxies & client-side scripting. Aside from JSON being literally just data, it violates HATEOAS, and in turn uniform interface, which already stops it from being referred to as RESTful. When editting data, we are provided 2 requests, PUT and PATCH. PUT is used to completely replace a resource, requiring inputs for every required field, with non-required being reset to the default. PUT should be used when a resource has many changes allocated to it. PATCH only alters one field of a resource typically. PATCH should be used when a resource only has 1-2 changes being allocated to it.
2. The models that we create are too complex for an API to handle. The serializer's job is to convert these complex objects into simple python objects that can easily be converted into JSON to be stored into the API. Aside from converting, it also has the opposite job of reconstructing when retrieving said objects. The benefit over manually building a dictionary with JSONResponse is that within the serializer we can add validation checks to make sure the data that is recieved is complete, valid, and safe from vulnerabilities. 
3. Authentication checks who you are and authorization checks what you are allowed to do. In DRF authentication is just the process of logging in, if you are logged in you pass the check. Authorization, on the other hand, checks your permissions to see what exactly you are allowed to do. Using a permission class makes sure a user that isn't allowed to do something is physically unable to (unless the web has vulnerabilities but thats a different matter). If you were to just hide a button in an attempt to stop someone from using it, they can very easily manipulate the page to make it accessible. Without any permission safety that endpoint is suddenly accessed by someone you don't want to.
4. SessionAuthentication isn't enough because browsers attach cookies to any request. If a random website happens to steal an innocent user's cookie they would suddenly be able to alter data they aren't supposed to if no CSRF token. Force authenticate isn't a valid CSRF test because it skips CSRF entirely, never getting forbiddden.
